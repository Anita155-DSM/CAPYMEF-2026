# Modelado de Base de Datos — CAPYMEF con FlexMind / FlexIDE

> Trabajo práctico: modelado de la base de datos del proyecto **CAPYMEF** aplicando el
> estándar de diseño de base de datos de **FlexMind / FlexIDE** (Gobierno de Formosa).
>
> Documentación de referencia:
> <https://flexdoc.formosa.gob.ar/manual/21/1/pasos_previos#diseno_de_base_de_datos>
>
> Alcance: **solo backend**. Se toman como base los modelos Sequelize actuales
> (`backend/models/*.js`) y se los reescribe respetando la normativa de FlexMind.

---

## 1. Qué es FlexMind / FlexIDE (contexto)

- **FlexMind** es un framework de desarrollo por **componentes** (grillas, formularios,
  subgrillas, reportes, procesos) configurados con archivos PHP + HTML mediante una
  librería de templates.
- **FlexIDE** es el entorno: administrador de código fuente, interfaz de desarrollo y
  **administrador de base de datos** (motor **MariaDB**).
- FlexMind **genera los módulos a partir de las tablas**: por eso el nombre de cada
  tabla y de cada columna debe seguir una nomenclatura estricta. El administrador de
  base de datos de FlexIDE genera automáticamente los prefijos y las constraints
  cuando la nomenclatura es correcta.
- Para desarrollar con FlexMind hay que respetar **dos estándares obligatorios**:
  1. Estructura de directorios.
  2. **Diseño de la base de datos** (lo que se documenta acá).

## 2. Convenciones de FlexMind aplicadas

### 2.1. Nombre de tablas — patrón `XXX_YYYY_NN_[T]_[Z]`

| Parte | Regla | En CAPYMEF |
|-------|-------|------------|
| `XXX` | 3 letras minúsculas `a-z` (sin `ñ` ni vocales acentuadas). Identifica el **subsistema**. | `cap` (CAPYMEF) |
| `YYYY` | 4 letras minúsculas `a-z`. Identifica el **módulo** dentro del subsistema. | `soci`, `finz`, `noti`, `audi` |
| `NN` | 2 dígitos `0-9`. Número **secuencial** de la tabla dentro del prefijo. | `01`, `02`, ... |
| `[T]` | Tipo de tabla: `cab` (cabecera), `det` (detalle), `arb` (árbol), `rel` (relación N:M), `hec` (hecho), `dim` (dimensión). | `cab`, `det` |
| `[Z]` | Descripción alfanumérica en minúscula (se permite `_`). | `socios`, `cuotas`, ... |

Ejemplo de la documentación: `sys_publ_01_cab_clientes`.
Ejemplo en CAPYMEF: `cap_soci_01_cab_socios`.

> El prefijo `flx_core_[N]_[Z]` está **reservado** para uso interno del framework: no usarlo.

### 2.2. Nombre de columnas — prefijo de 9 caracteres `XXXYYYYNN`

El prefijo de columna es la concatenación **sin guiones bajos** de `XXX` + `YYYY` + `NN`.
Para `cap_soci_01_...` el prefijo de columna es **`capsoci01`**.

| Elemento | Patrón | Ejemplo |
|----------|--------|---------|
| **Clave primaria** | `id_XXXYYYYNN` — **numérica y autoincremental** (obligatorio) | `id_capsoci01` |
| **Campo común** | `XXXYYYYNN_[Z]` | `capsoci01_razon_social` |
| **Clave foránea** | `rela_XXXYYYYNN` → apunta al prefijo de 9 caracteres de la tabla relacionada | `rela_capsoci02` |
| **Autorreferencia** | `rela_padre` | `rela_padre` |

### 2.3. Constraints

| Objeto | Patrón | Ejemplo |
|--------|--------|---------|
| Foreign key | `fk_XXXYYYYNN_MM` — `XXXYYYYNN` = prefijo de la tabla **maestra (referenciada)**, `MM` = correlativo `01-99` por cada FK que apunta a esa maestra | `fk_capsoci01_01` |
| Unique (criterio propio para este TP) | `uq_XXXYYYYNN_MM` | `uq_capsoci01_01` |

### 2.4. Funciones (para lógica de negocio en FlexMind)

Patrón `aaa_bbb_ccc` o `aaaBbbCcc`:
- `aaa` = módulo/concepto (`cuotas`, `pagos`, `socios`)
- `bbb` = operación (`sum`, `getStr`, `getInt`, `count`)
- `ccc` = detalle

Ejemplo: `cuotas_sum_pendientesPorSocio`.

## 3. Decisiones de adaptación (Sequelize → FlexMind)

El proyecto actual usa PostgreSQL + Sequelize. Al migrar el **modelo** a la normativa
FlexMind (MariaDB) se toman estas decisiones:

| Situación en el modelo actual | Decisión en el modelo FlexMind | Motivo |
|-------------------------------|--------------------------------|--------|
| PK `UUID` en `Cuota`, `Pago`, `Gasto` | Se reemplaza por `id_XXXYYYYNN` **INT AUTO_INCREMENT** | FlexMind exige PK numérica autoincremental |
| Campos `ENUM` (`categoria`, `rubro`, `estado`, `visibilidad`, `metodoPago`, ...) | Se convierten en **tablas catálogo `cab`** + FK `rela_` | FlexMind modela los valores de dominio como tablas relacionadas, no como ENUM |
| `paranoid: true` (borrado lógico de Sequelize) | Columna `XXXYYYYNN_deleted_at DATETIME NULL` + `XXXYYYYNN_estado TINYINT(1)` | Se conserva el borrado lógico con nomenclatura FlexMind |
| `timestamps: true` (`createdAt` / `updatedAt`) | `XXXYYYYNN_created_at` / `XXXYYYYNN_updated_at` | Auditoría estándar de cada fila |
| `Auditoria.usuarioId` (INT suelto, sin FK) | `rela_capsoci01` **NULL** con `ON DELETE SET NULL` + se mantienen las columnas denormalizadas `usuario_nombre` / `usuario_rol` | El log debe sobrevivir aunque se borre el socio |
| `metodoPago` (Pago) vs `medio_pago` (Gasto) con valores distintos | Un único catálogo `cap_finz_05_cab_metodos_pago` con la unión de valores | Evita duplicar el mismo concepto |

### 3.1. Columnas estándar de auditoría (todas las tablas transaccionales)

| Columna | Tipo | Regla |
|---------|------|-------|
| `XXXYYYYNN_estado` | `TINYINT(1) NOT NULL DEFAULT 1` | 1 = activo, 0 = inactivo (baja lógica rápida) |
| `XXXYYYYNN_created_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` | Alta de la fila |
| `XXXYYYYNN_updated_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | Última modificación |
| `XXXYYYYNN_deleted_at` | `DATETIME NULL` | Borrado lógico (solo tablas que hoy son `paranoid`) |


Cardinalidades:

| Relación | Tipo | Regla de negocio |
|----------|------|------------------|
| socios → cuotas | 1 : N | Un socio tiene muchas cuotas mensuales |
| cuotas → pagos | 1 : 1 | Una cuota se salda con un único pago (`UNIQUE` sobre la FK) |
| socios → pagos | 1 : N | Un socio realiza muchos pagos |
| categorías / rubros / tamaños / estados / roles → socios | 1 : N | Catálogos de dominio del socio |
| estados_cuota → cuotas | 1 : N | Catálogo de estado de la cuota |
| métodos_pago → pagos / gastos | 1 : N | Catálogo de medio de pago compartido |
| visibilidades / estados_noticia → noticias | 1 : N | Catálogos de dominio de la noticia |
| socios → auditorías | 1 : N (opcional) | `rela_capsoci01` NULL, `ON DELETE SET NULL` |

> **No hay relaciones N:M** en el dominio actual. Si más adelante se agregan
> *etiquetas de noticias*, se modelaría con una tabla `rel`:
> `cap_noti_04_rel_noticias_etiquetas` con las columnas `rela_capnoti01` y
> `rela_capnoti05` (hacia `cap_noti_05_cab_etiquetas`).

## 8. Pasos previos aplicados (checklist del TP)

1. **Estándares obligatorios** reconocidos: estructura de directorios + diseño de BD. Este documento cubre el segundo.
2. **Prefijos de esquema definidos:** subsistema `cap`; módulos `soci`, `finz`, `noti`, `audi`.
3. **Tablas nombradas** con el patrón `XXX_YYYY_NN_[T]_[Z]` (ver §4.1).
4. **Columnas nombradas** con prefijo de 9 caracteres:
   - PK `id_XXXYYYYNN` numérica autoincremental.
   - Campos `XXXYYYYNN_[Z]`.
   - FK `rela_XXXYYYYNN`; autorreferencia `rela_padre` (no se usa en este dominio).
5. **Constraints FK** nombradas `fk_XXXYYYYNN_MM` tomando el prefijo de la tabla maestra.
6. **Dominios (ENUM) convertidos** a tablas catálogo `cab` con sus datos semilla.
7. **Auditoría estándar** (`estado`, `created_at`, `updated_at`, `deleted_at`) agregada a las tablas transaccionales.
8. **Modelo listo** para cargarse en el administrador de base de datos de FlexIDE (MariaDB), que genera prefijos y constraints automáticamente y a partir de ahí los módulos FlexMind (grillas y formularios).
